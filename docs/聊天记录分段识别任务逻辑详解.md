# 聊天记录分段识别任务逻辑详解

## 1. 文档目的

本文梳理项目中“从聊天记录中识别任务内容”的完整实现链路。结合当前代码，这一能力的产品语义并不是“通用待办抽取”，而是：

- 从单个会话或多个群聊中抓取最近一段时间的消息
- 过滤为可分析的文本消息
- 将消息按批次切段
- 交给 AI 提取“商机 / 资源类重要信息”
- 对结果进行解析、去重、落库
- 在 AI 失败或模型返回空时启用规则兜底

当前实现的主要识别对象包括：

- 招聘信息
- 求购 / 采购信息
- 资源需求
- 找老师 / 找专家 / 顾问类信息

## 2. 整体架构与调用链

### 2.1 Electron 一体化结构

应用采用 Electron 桌面架构：

- 主进程启动时 fork 一个本地 Express 服务，自动寻找可用端口。[main.js](file:///d:/source/fantastic-funicular-main/src/main/main.js#L138-L167)
- 渲染进程通过 `preload` 暴露的 `getServerPort()` 获取后端端口。[preload.js](file:///d:/source/fantastic-funicular-main/src/main/preload.js#L5-L11)
- 前端后续所有识别任务都通过本地 HTTP 调用接口，而不是直接调用 Node 服务对象。[app.js](file:///d:/source/fantastic-funicular-main/src/renderer/app.js#L315-L342)

### 2.2 一次识别任务的主时序

完整链路可以概括为：

1. 用户点击单会话或批量识别按钮
2. 前端调用 `/api/ai/status` 检查 AI 是否就绪
3. 前端调用 `/api/wechat/messages/:chatId` 获取聊天消息
4. 前端只保留 `type === 'text'` 的消息
5. 前端把消息数组提交到 `/api/todos/generate-from-chat`
6. 后端 `TodoService.generateFromChat()` 先做消息级去重
7. 后端把剩余消息按字符数切成多个 batch
8. 每个 batch 交给 `AIService.extractTodos()` 生成结构化结果
9. `AIService` 解析 JSON，统一字段
10. `TodoService` 做结果级去重并落库
11. 若 AI 全部无结果，则启用正则兜底抽取
12. 前端刷新待办列表并提示结果

## 8. 分段识别的核心：按字符数切批

这部分是“聊天记录分段识别”的核心实现。

### 8.1 为什么要切段

整段聊天如果过长，会有多个问题：

- 模型输入过长，成本高
- 本地模型更容易崩溃
- 输出容易跑偏
- 某一批失败会拖垮整轮识别

所以系统在后端把消息切成多个批次再识别。

### 8.2 批次单位

每条消息先被标准化成：

```text
[时间] [发送者]: 内容
```

代码：

- [TodoService.js](file:///d:/source/fantastic-funicular-main/src/services/TodoService.js#L141-L156)

### 8.3 切批规则

当前阈值：

- `MAX_CHARS_PER_BATCH = 2500`

切分逻辑：

- 遍历消息
- 逐条计算当前 batch 长度
- 如果加入下一条后超过 2500 字符，则先把当前 batch 入列
- 再开启新 batch

代码：

- [TodoService.js](file:///d:/source/fantastic-funicular-main/src/services/TodoService.js#L136-L160)

### 8.4 调用方式

每个 batch 单独执行：

- 拼接 `chatContent`
- 调 `aiService.extractTodos(chatContent)`
- 成功结果放入总的 `extractedTodos`

代码：

- [TodoService.js](file:///d:/source/fantastic-funicular-main/src/services/TodoService.js#L167-L177)

### 8.5 容错方式

每个 batch 失败不会立刻中断全流程：

- 错误先记到 `firstBatchError`
- 继续处理后续 batch
- 如果最终至少有一个 batch 成功提取，则整体仍算成功
- 只有“所有批次都没有结果，且至少一批报错”时，才整体抛错

代码：

- [TodoService.js](file:///d:/source/fantastic-funicular-main/src/services/TodoService.js#L178-L188)

这意味着当前实现是“部分成功优先”的容错策略。

## 11. JSON 解析与标准化

AI 返回内容并不总是规范 JSON 数组，因此 `extractTodos()` 做了多层兼容。

### 11.1 解析顺序

1. 先直接 `JSON.parse(response)`
2. 若失败，尝试从文本里匹配一个对象块 `{...}`
3. 若对象块没有，再尝试匹配数组块 `[...]`

代码：

- [AIService.js](file:///d:/source/fantastic-funicular-main/src/services/AIService.js#L252-L268)

### 11.2 兼容结构

系统兼容以下几种格式：

- 直接数组：`[ {...}, {...} ]`
- 包装对象：`{ items: [...] }`
- 包装对象：`{ results: [...] }`
- 包装对象：`{ data: [...] }`
- 单对象：`{ title: "...", ... }`

代码：

- [AIService.js](file:///d:/source/fantastic-funicular-main/src/services/AIService.js#L270-L280)

### 11.3 字段清洗

最终结果统一被清洗为：

- 标题最多 200 字符
- 描述最多 1000 字符
- 优先级只接受 `high / medium / low`
- `dueDate / sender / messageTime` 缺失时用 `null`

代码：

- [AIService.js](file:///d:/source/fantastic-funicular-main/src/services/AIService.js#L282-L297)

### 11.4 失败策略

- 资源：`找资源|寻找资源|找渠道|找合作|找场地`

- `priority`
- `dueDate`

代码：

- [TodoService.js](file:///d:/source/fantastic-funicular-main/src/services/TodoService.js#L287-L290)

## 13. 结果级去重与落库

### 13.1 去重规则 1：同发送者 + 同时间

如果同群内已经存在：

- `existing.messageTime === todoData.messageTime`
- `existing.sender === todoData.sender`

就视为重复。

代码：

- [TodoService.js](file:///d:/source/fantastic-funicular-main/src/services/TodoService.js#L205-L210)

### 13.2 去重规则 2：标题完全一致

## 16. 当前实现的边界与特点

### 16.1 优点

- 架构清晰，前后端职责分离
- 支持单会话与批量两种入口
- 支持按小时过滤，避免全量扫描
- 支持分页抓取消息，避免单次遗漏
- 支持单群内分段识别，降低大输入风险
- 支持模型失败回退
- 支持 JSON 多格式兼容
- 支持规则兜底
- 支持两层去重，避免重复落库

### 16.2 局限

- 当前默认目标仍然是“商机 / 资源类重要信息”，不是所有通用待办
- 前端只处理文本消息，链接类招聘信息可能会被过滤掉
- 解析失败与真正无结果都可能表现成 0 条
- 字符数切批较简单，不按语义边界切分
- 兜底规则是关键词规则，不具备深层语义理解

## 17. 一段聊天记录是如何被“分段识别”为任务内容的

用一句更工程化的话概括当前方法：

> 系统先从微信数据库分页拉取最近时间窗口内的文本消息，再在后端按固定字符上限切成多个批次；每个批次被格式化为“[时间] [发送者]: 内容”的纯文本块，送入 AI 提示词进行结构化抽取；AI 返回结果经过多格式 JSON 解析、字段清洗和两层去重后写入待办；若 AI 为空，则用正则规则对招聘、求购、资源、专家类文本做兜底提取。

这就是当前“聊天记录分段识别任务内容”的完整方法论。
